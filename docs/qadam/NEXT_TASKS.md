# NEXT_TASKS — что делать дальше

Задачи следующему агенту, по убыванию важности. Контекст проекта, доступы и
ловушки — в [HANDOFF](HANDOFF.md); прочитать его до первой строки кода.

У каждой задачи есть проверка «сделано». Задача без прохождения этой проверки
не сделана, даже если код написан.

---

## P0 — объединить демо и боевой режим в один стенд

**Это прямое требование владельца.** Одна ссылка, где посетитель может
попробовать и демонстрационный, и боевой режим, не уходя на другой адрес.

Полный разбор — [HANDOFF §5](HANDOFF.md#5-задача-один-стенд-вместо-двух).
Коротко: разделение **уже проходит по строкам**, а не по окружению. У заведения
есть колонка `businesses.mode` (`demo`/`production`), и база держит её
констрейнтом `(mode='demo' and is_mock) or (mode='production' and not is_mock)`
плюс триггером `mock rows are forbidden in production businesses`.
`QADAM_APP_MODE` — глобальный гейт поверх, стоящий в девяти перечисленных
местах. Работа в том, чтобы перевести поведенческие решения на режим заведения,
а переменную окружения свести к потолку стенда.

Сделано, когда:

- на одном адресе посетитель выбирает «посмотреть демо» или «зарегистрировать
  своё заведение», и оба пути работают;
- в демо-заведении доступны скачок во времени и симуляции, в своём —
  нет, и запуск без подключённого канала отклоняется с честным объяснением;
- попытка записать `is_mock`-строку в заведение с `mode='production'`
  отвергается базой (это проверяется, а не предполагается);
- `tests/release/mode-separation.mjs` переписан: он должен доказывать
  разделение **по заведениям на одном сервере**, а не поднимать два сервера с
  разными переменными;
- `DEPLOY_RUNBOOK` части D и E, `PRODUCT_CONSTITUTION`, `REAL_VS_MOCK` и
  `KNOWN_LIMITATIONS` обновлены в том же коммите — сейчас они объявляют
  `DEMO_MODE` на общем окружении инцидентом, и после объединения это перестанет
  быть правдой.

**Согласовать с владельцем до начала:** пункт про документы — это решение
продукта, а не рефакторинг. Гарантия честности не исчезает, она переезжает с
уровня развёртывания на уровень строки, но сказать об этом обязаны документы, а
не только код.

## P1 — то, что не доделано и это видно

### 1.1 Цикл выполнения не запускается на стенде

Планировщика нет, и это не теория. На демо-стенде сейчас: активная
автоматизация — 1, запусков автоматизаций — 0, событий в очереди отправки со
статусом `pending`/`failed` — 1. Ничего не двигается само.

`/api/jobs/run-cycle` ждёт **POST** с заголовком `x-qadam-job-secret`. Vercel
Cron на бесплатном тарифе ходит **GET** и **раз в сутки**, без кастомных
заголовков, — как есть не подойдёт.

Варианты, выбрать осознанно:

| Вариант | Плюсы | Минусы |
|---|---|---|
| GET-роут `/api/cron/tick`, проверяющий `Authorization: Bearer $CRON_SECRET` | Работает штатно, без внешних сервисов | Раз в сутки на бесплатном тарифе — для демо почти бесполезно |
| Внешний пингер (cron-job.org, GitHub Actions по расписанию) | Минута и чаще, ничего не меняется в продукте | Ещё одна внешняя зависимость и ещё один секрет |
| `pg_cron` в Supabase, дергающий функцию напрямую | Без HTTP-периметра | Логика исполнения живёт в приложении, а не в базе — придётся дублировать |

Сделано, когда автоматизация с наступившим сроком запускается сама, в
`automation_runs` появляется запись, и очередь отправки перестаёт копиться.
Не забудьте, что защита от повтора в `/api/jobs/run-cycle` живёт в памяти
процесса — на нескольких инстансах она не работает, это уже записано в
`KNOWN_LIMITATIONS`.

### 1.2 Автодеплой из GitHub не подключён

Сейчас деплой только руками: `vercel deploy --prod` из локальной папки.
Подключить репозиторий к проекту Vercel (`vercel git connect`) или настроить
GitHub Actions. Сделано, когда push в `master` сам обновляет стенд, а упавший
`npm run verify` его не обновляет.

### 1.3 Наборы, ни разу не прогонявшиеся против стенда

- `npm run test:perf` — использует тот же харнесс, значит теперь запустится
  против стенда. Учтите: проверки размера бандла смотрят на **локальную**
  сборку, а тайминги — на удалённую; не смешивайте выводы.
- `npm run db:test` (pgTAP) — требует локального стека, против удалённого
  проекта не пойдёт. Либо оставить локальным и сказать об этом прямо, либо
  научить ходить через Management API, как это сделано для E2E.
- `npm run test:release` — полный аудит, включая гейты G1–G12. Против стенда ни
  разу не гонялся.

Сделано, когда для каждого набора записано: прошёл против стенда с таким-то
результатом, либо не применим к стенду по такой-то причине.

## P2 — качество и честность

### 2.1 Два предупреждения советника безопасности

`private.platform_admin_assignments` и `public.platform_events` имеют включённый
RLS без единой политики. Похоже на намеренный deny-all — доступ идёт через
security-definer функции. Подтвердить это чтением кода, а затем либо записать
решение в `DECISIONS.md`, либо добавить явные политики. Молча оставлять
предупреждение нельзя: следующий человек не отличит намерение от упущения.

### 2.2 Тренировка восстановления из бэкапа

`KNOWN_LIMITATIONS` и `RUNBOOK` говорят, что процедура описана, но ни разу не
выполнялась — раньше не на чем было. Теперь есть два удалённых проекта, и
тренировку наконец можно провести на том, который не показывают судьям.
Сделано, когда в `RUNBOOK` записаны дата, длительность и то, что пошло не так.

### 2.3 Казахский язык

Тексты внутри кабинета на русском и помечены `native_review_required`.
Интерфейс об этом честно сообщает, так что это не обман — но и не готовность.
Либо найти носителя для проверки, либо явно ограничить интерфейс русским.

### 2.4 Политика паролей

`password_min_length = 6`, `password_required_characters` не задан. Защита от
утёкших паролей (HIBP) у Supabase только на платном тарифе — включить нельзя,
это ограничение плана, а не настройка. Решить, поднимать ли минимальную длину;
это решение продукта, поэтому согласовать, а не менять молча.

### 2.5 Холодный старт

Первый запрос к боевому стенду после простоя занимает около пяти секунд —
холодный старт функции. Для демонстрации важно: судья, открывающий ссылку
первым, увидит именно это. Померить, решить, нужен ли прогрев.

## P3 — гигиена

- `.env.local` содержит `VERCEL_OIDC_TOKEN`, дописанный командой `vercel link`.
  Локальной разработке не мешает, но знать стоит.
- На боевом проекте остался один тестовый арендатор от проверки регистрации.
  База отказалась его удалять: сработал инвариант «нельзя убрать последнего
  владельца». Это её правильное поведение, а не дефект; удалять — только через
  передачу владения или удаление заведения целиком.
- Восстановление стенда — две команды с ref. Стоит свести к одной npm-команде.
- Проект Supabase `xeawgjbywhubnkuxtgho` после объединения освободится. Не
  удалять сразу: чистая схема без демо-данных — удобный эталон для сверки и
  площадка для тренировки из 2.2.

## С чего начать в первый час

1. Прочитать [HANDOFF](HANDOFF.md) целиком, особенно §3 (ловушки) и §5 (задача).
2. `npm ci && npm run dev:all` — поднять локально, убедиться, что
   `npm run verify` проходит на чистом дереве. Нужен запущенный Docker Desktop.
3. Прогнать E2E против живого стенда и получить 58/58, 36/36, 45/45. Если
   числа другие — разбираться до того, как менять код: значит стенд или
   окружение уже не такие, как описано.
4. Вернуть стенд к исходным данным после прогона (`remote_demo_reset.sql`,
   затем `remote_demo_seed.sql`).
5. Только после этого браться за P0.

## Чего делать нельзя

- Ослаблять констрейнт `(mode='demo' and is_mock) or (mode='production' and not
  is_mock)` или триггер `mock rows are forbidden in production businesses`.
  После объединения режимов именно они держат всю гарантию честности.
- Удалять строку из `private.demo_environment` на демо-проекте или добавлять её
  на боевой.
- Применять `supabase/seed.sql` где-либо, кроме локальной машины.
- Класть `SUPABASE_SECRET_KEY` в переменную с префиксом `NEXT_PUBLIC_`.
- Коммитить секреты: репозиторий публичный. Ключи лежат в `CREDENTIALS.local.md`,
  который в `.gitignore`; перед коммитом проверять
  `git check-ignore -v CREDENTIALS.local.md`.
- Отмечать канал `connected` без пройденной проверки связи — база откажет, и
  это правильно.
