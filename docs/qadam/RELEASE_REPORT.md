## 4. Critical security findings

Найдено и **исправлено** в этом прогоне.

### 4.1 CRITICAL — TRUNCATE обходит row level security

`anon` и `authenticated` имели `TRUNCATE`, `TRIGGER` и `REFERENCES` на 65 таблицах — это
поведение по умолчанию при бутстрапе Supabase. **Постгрес не применяет политики строк к
TRUNCATE.** Воспроизведено на живой базе: владелец тенанта B, который не видит **ни одной**
строки тенанта A, выполнил `truncate public.customers cascade` и каскадно уничтожил
идентичности, согласия, транзакции, счета лояльности, события кампаний, погашения и privacy-
запросы **всех тенантов платформы**.

Исправлено миграцией `20260802020000_revoke_rls_bypassing_grants.sql`: три привилегии
отозваны у `anon` и `authenticated`, вместе с default privileges, чтобы новая таблица их не
получила; `anon` дополнительно лишён INSERT/UPDATE/DELETE. `service_role` не тронут — это
серверный ключ, который никогда не попадает в браузер.

Регрессия закрыта двумя способами: `check:data-layer` требует наличия этого отзыва в
миграциях, а RLS-матрица заново пытается выполнить truncate и требует отказа.

### 4.2 HIGH — не было ни одного заголовка безопасности

Ответы не содержали ни CSP, ни HSTS, ни `X-Frame-Options`, ни `Referrer-Policy`, ни
`Permissions-Policy`, зато сообщали `X-Powered-By: Next.js`. Добавлен
`src/lib/security/headers.ts`, применяемый прокси ко **всем** ответам, включая редиректы.
CSP на аутентифицированных маршрутах — `script-src 'self'` плюс nonce на каждый запрос
(проверено, что nonce разный); `form-action 'self'` не даёт отправить форму запуска кампании
на чужой сервер, `frame-ancestors 'none'` закрывает clickjacking.

### 4.3 HIGH — 3 уязвимости в зависимостях

`postcss` ≤8.5.17 (XSS через неэкранированный `</style>`, чтение файлов через
`sourceMappingURL`) и `sharp` <0.35.0 (четыре CVE в libvips), обе транзитивно через `next`.
`npm audit fix --force` предлагал откатить Next до 9.3.3 — это было отвергнуто. Вместо
этого добавлены `overrides`, которые поднимают только уязвимые зависимости.
Результат: **0 находок любой серьёзности**, сборка и все тесты проходят.

### 4.4 Проверено и подтверждено работающим

Изоляция тенантов на **всех 67 тенантных таблицах** (чтение, попытка присвоить чужой
`business_id`, вставка в чужой тенант); анонимный доступ ограничен четырьмя справочными
таблицами; CSRF защищён — server action с чужим `Origin` не меняет данных, а тот же вызов
с правильным Origin меняет; sign-out только POST; job-эндпоинт требует секрет в постоянном
времени, не даёт повторить cycle key и включает rate limit на 11-м вызове; webhook отвергает
неподписанное, неверно подписанное и **корректно подписанное, но просроченное** событие,
а повтор не создаёт второй записи; XSS-payload в заметке о клиенте сохраняется как данные,
рендерится экранированным и не вызывает диалога; SQL-подобный payload не роняет таблицу;
кривая строка импорта возвращает `{"invalid": 1}` и не создаёт клиента; все SECURITY DEFINER
функции фиксируют `search_path`.

## 8. CI

`.github/workflows/ci.yml` — четыре независимые задачи:

- **static** — `npm ci` строго из lockfile, lint, типы, unit, разметка, граница секретов, сборка;
- **database** — чистый старт Supabase (это и есть реплей миграций), запрет продакшн-seed,
  контракт слоя данных, pgTAP, RLS-матрица, статический скан, schema lint, advisors и
  **проверка дрейфа сгенерированных типов**;
- **e2e** — сборка, продакшн-сервер, три acceptance-набора, HTTP-сьют, a11y-аудит,
  выгрузка скриншотов и JSON как артефактов;
- **secrets** — gitleaks по всей истории и запрет коммита `.env`.

`.github/workflows/deploy.yml` запускается только после успешного CI и **падает**, если
CI завершился иначе. Оба шага деплоя сейчас честно отказывают: нет привязанного проекта
Supabase и нет хостинга. Seed в общие окружения не применяется никогда.

Разделение окружений: `dev` — локальная машина; `staging` и `production` — GitHub
Environments со своими секретами, каждый требует собственный `SUPABASE_PROJECT_REF`.

## 9. Remaining blockers

**BLOCKED** — внешние, не обходятся:

1. **Платёжный провайдер не подключён.** Live billing невозможен; `createBillingProvider`
   отказывает в обоих режимах, `billing_events` пуст. Чек-лист подключения в RUNBOOK.
2. **Нет sandbox-доступа к WhatsApp / Telegram / Instagram.** Ни один канал не может дойти
   до `connected`, поэтому `verified_fact` не может существовать — база это запрещает.
3. **Юридическая проверка для Казахстана не проводилась.** Указано на самой `/privacy`.
4. **Нет удалённого проекта Supabase.** Процедура восстановления описана, но не выполнялась.
5. **Нет платформенного планировщика.** Цикл запускает внешний вызов; rate limit и
   защита от повтора живут в памяти процесса и потребуют общего хранилища при нескольких
   инстансах.

**PARTIAL** — сделано частично, честно помечено:

6. **Переключатель RU/KK клиентский.** Выбор хранится в `localStorage` и переживает
   навигацию, но серверный рендер всегда русский.
7. **Пять курируемых наборов шаблонов** не написаны — есть только машинерия версионирования.
8. **`style-src` содержит `'unsafe-inline'`**, а маркетинговые страницы используют
   `script-src 'unsafe-inline'`, потому что статический пререндер не может нести nonce.
9. **Нагрузочный тест — один локальный инстанс.** Это не заявление о ёмкости платформы.
10. **Партиционирование не введено** — пороги и стратегия записаны в RUNBOOK.

## 10. Точный следующий шаг
