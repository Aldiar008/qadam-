# HANDOFF — QADAM Growth OS

Передача проекта следующему агенту. Документ описывает три вещи: что уже
работает, на чём легко потерять время, и что предстоит сделать.

Дата передачи: 2026-08-02.

---

## 1. Что это за проект

AI-маркетолог для малого офлайн-бизнеса в Казахстане. Next.js 16 (App Router,
server actions) + Supabase (Postgres 17, RLS на всех тенантных таблицах).
26 миграций, 80 таблиц.

Главный принцип продукта — **честность**: демонстрационные данные помечены
`is_mock` и никогда не выдаются за проверенный факт; канал не может стать
`connected` без пройденной проверки связи; запуск без подключённого провайдера
отклоняется, а не имитируется. Эти гарантии держатся не соглашениями, а
констрейнтами и триггерами в базе — ломать их нельзя, и обходить их в коде
приложения бессмысленно, база всё равно откажет.

Обязательное чтение перед первым изменением:
[PRODUCT_CONSTITUTION](PRODUCT_CONSTITUTION.md), [ARCHITECTURE](ARCHITECTURE.md),
[REAL_VS_MOCK](REAL_VS_MOCK.md), [KNOWN_LIMITATIONS](KNOWN_LIMITATIONS.md).

## 3. Ловушки, на которых легко потерять час

1. **`supabase db push` на CLI 2.110 не работает.** Падает
   `LegacyDbPushApplyError: Connection error` посреди миграции, воспроизводимо,
   и на прямом хосте, и на пулере. Тот же SQL через Management API проходит
   мгновенно — значит дело в CLI, а не в SQL. Старые CLI не понимают текущий
   `config.toml` (`'db' has invalid keys: health_timeout`).
   **Что работает:** скопировать `supabase/migrations` во временную папку с
   `config.toml`, содержащим только `project_id`, и оттуда выполнить
   `npx -y supabase@2.64.1 db push --db-url <URL пулера, порт 5432>`.
   Пароль в URL кодировать (`/` → `%2F`).

2. **Справочные данные кладут миграции, а не seed.** Тарифы, их лимиты,
   `entitlements`, `retention_policies`, `data_inventory`. Локально это
   невидимо, потому что `supabase db reset --local` проигрывает миграции
   вместе с seed. На удалённом стенде возвращается только seed. Если стереть
   эти таблицы, заведение без подписки откатывается на тариф `free`, не находит
   его — и сборка Growth Contract отказывает сообщением
   «Тариф none: 0/0 за период», в котором ничто не указывает на причину.
   `supabase/seed/remote_demo_reset.sql` эти пять таблиц не трогает и в конце
   проверяет, что `free` и его лимит `growth_contracts_month` на месте.

3. **Сеть до `api.supabase.com` и до стендов рвётся.** На машине владельца
   регулярно ловятся `UND_ERR_CONNECT_TIMEOUT` и `ERR_CONNECTION_RESET`.
   `scripts/apply-remote-sql.mjs` и `tests/e2e/remote-query.mjs` уже делают
   повторы. Если пишете новый инструмент, ходящий к Management API, —
   закладывайте повторы сразу, иначе потерянный шаг в паре «сброс, затем seed»
   оставит стенд пустым.

4. **Не гоняйте два набора против одного стенда одновременно.** Они делят одну
   базу, и прогон, который начинается со сброса, снесёт данные под соседним.
   Один раз это уже дало ложное падение.

5. **`private.demo_environment`** — таблица-метка. Пустая на боевом проекте,
   с одной строкой на демонстрационном. Демо-seed и сброс отказываются работать
   на базе без этой строки. Это единственное, что не даёт демо-данным попасть
   в боевую базу, — не удаляйте.

6. **HIBP (защита от утёкших паролей)** у Supabase только на платном тарифе.
   Советник безопасности будет ругаться, включить нельзя.

7. **Планировщика нет.** `/api/jobs/run-cycle` ждёт POST с заголовком
   `x-qadam-job-secret`. Vercel Cron на бесплатном тарифе ходит раз в сутки и
   без кастомных заголовков, то есть как есть не подойдёт. В DEMO_MODE цикл
   двигает «скачок во времени» из интерфейса.

## 4. Что было сделано в предыдущей сессии

Всё закоммичено в `master`. Каждое изменение — следствие того, что ломалось
именно на развёрнутом стенде и не могло проявиться локально.

- **Адаптер Gemini** (`src/ai/providers.ts`). `gemini-2.5-flash` новым ключам
  больше не выдают; 3.x отвечает 400 на `thinkingBudget` и требует
  `thinkingLevel`. Форма выбирается по поколению модели из её имени
  (`thinkingConfigFor`), неузнанное имя не шлёт ничего.
- **Метка демо-окружения** — миграция `20260802040000`, таблица
  `private.demo_environment`. Метка уровня базы не подошла: Supabase не даёт
  роли `postgres` определять параметр базы.
- **`scripts/apply-remote-sql.mjs`** — применяет один SQL-файл к удалённому
  проекту через Management API (`db push` умеет только миграции, psql стоит не
  везде).
- **`supabase/seed/remote_demo_seed.sql`** — генерируется из `supabase/seed.sql`
  скриптом `npm run seed:remote`; локальный guard не удаляется, а
  перенаправляется на `private.demo_environment`.
- **`supabase/seed/remote_demo_reset.sql`** — возвращает демо-стенд к seed.
- **Приёмочные наборы научились работать против деплоя:** проверки, читающие
  базу, идут через Management API при заданном `QADAM_SUPABASE_PROJECT_REF`;
  раннер восстанавливает удалённый стенд вместо сброса локальной базы; пороги
  ожиданий масштабируются множителем `PATIENCE` (localhost — 1, удалённая цель
  — 4).
- **Исправление в продукте:** платформенный администратор после входа уходил
  на онбординг, потому что членства в заведении у него нет по устройству.
  Теперь отсутствие членства проверяется на платформенную роль через
  `is_current_platform_admin` (`src/app/auth/actions.ts`).

## 5. Задача: один стенд вместо двух

**Что просит владелец.** Один проект и одна ссылка, где посетитель может
попробовать и демонстрационный, и боевой режим, не переходя на другой адрес.

**Хорошая новость: половина этого уже есть в схеме.** Режим — не только
переменная окружения. У заведения есть собственный режим:

```sql
-- supabase/migrations/20260730044603_qadam_foundation.sql
mode text not null default 'production' check (mode in ('demo','production'))
check ((mode='demo' and is_mock) or (mode='production' and not is_mock))
```

И база держит это всерьёз: триггер из `20260730044621` поднимает
`mock rows are forbidden in production businesses`, а полтора десятка
security-definer функций выводят `is_mock` именно из `businesses.mode`.
То есть **разделение уже проходит по строкам, а не по окружению**. Оба
существующих заведения на демо-стенде — `mode='demo'`; любая новая регистрация
получает `mode='production'` по умолчанию.

`QADAM_APP_MODE` — это дополнительный глобальный гейт поверх, и он стоит
ровно в девяти местах:

| Файл | Что делает гейт |
|---|---|
| `src/lib/supabase/proxy.ts:31` | закрывает маршрут `/demo` вне DEMO_MODE |
| `src/app/layout.tsx:55` | `AppModeProvider demoEnabled=…` |
| `src/app/auth/actions.ts:70` | `demoLogin` отказывает вне DEMO_MODE |
| `src/app/app/analytics/actions.ts:23` | скачок во времени |
| `src/app/app/analytics/page.tsx:31` | показ демо-элементов |
| `src/app/app/automations/actions.ts:161` | передаёт `appMode` в исполнение |
| `src/app/app/campaigns/studio/launch-actions.ts:135` | отказ в запуске без канала |
| `src/app/q/[token]/actions.ts:11` | QR-скан помечается `simulated` |
| `src/billing/provider.ts:109` | подпись неподключённого биллинга |

**Предлагаемое направление** (не приказ, обоснуйте своё, если увидите лучше):

1. Каждый поведенческий гейт читает `businesses.mode` текущего заведения, а не
   переменную окружения. Строки 23, 31, 161, 135, 11, 109 из таблицы выше — это
   решения про **конкретное заведение**, и у них уже есть правильный источник.
2. `QADAM_APP_MODE` остаётся, но меняет смысл: это **потолок стенда**, а не
   решение. Переименуйте честно (например `QADAM_DEMO_TENANTS_ENABLED`) и
   оставьте за ним только три вещи: существует ли кнопка демо-входа, открыт ли
   маршрут `/demo`, и разрешено ли вообще заводить заведения с `mode='demo'`.
   Стенд, где демо запрещено целиком, должен остаться выразимым.
3. Одна база: демо-заведения и настоящие живут рядом, разделённые RLS и
   `businesses.mode`. Констрейнт и триггер уже не дают mock-строке попасть в
   боевое заведение — именно это делает совместное проживание допустимым.
4. Посетитель выбирает на входе: «Посмотреть демо» (вход в TAMYR Coffee,
   `mode='demo'`) или «Зарегистрировать своё заведение» (`mode='production'`,
   честные отказы, никаких симуляций).

**О чём нужно сказать владельцу прямо, а не молча сделать.** Сейчас
[DEPLOY_RUNBOOK](DEPLOY_RUNBOOK.md) часть D говорит: «Ставить
`QADAM_APP_MODE=DEMO_MODE` на общем окружении — инцидент», а часть E описывает
демо-стенд как отдельное третье окружение. После объединения это перестанет
быть правдой. Гарантия честности не исчезает — она переезжает с уровня
развёртывания на уровень строки, где её держат констрейнт и триггер, — но
документы обязаны говорить то, что есть на самом деле. Обновите D и E,
[PRODUCT_CONSTITUTION](PRODUCT_CONSTITUTION.md), [REAL_VS_MOCK](REAL_VS_MOCK.md)
и [KNOWN_LIMITATIONS](KNOWN_LIMITATIONS.md) в том же коммите, что и код.

**Что сломается и требует переделки:**

- `tests/release/mode-separation.mjs` собирает и поднимает **два сервера** с
  разными переменными окружения. После объединения он должен доказывать другое:
  что на **одном** сервере демо-заведение и боевое ведут себя по-разному —
  скачок во времени доступен в первом и отсутствует во втором, запуск без
  канала отклонён во втором, mock-строка в боевом заведении отвергается базой.
- `tests/security/http-suite.mjs:211` проверяет `QADAM_APP_MODE` как признак
  сборки — проверка станет бессмысленной в текущем виде.
- `src/app/login/layout.tsx` содержит комментарий про режим как
  deploy-time конфигурацию — он станет неверным.
- `scripts/dev-all.mjs:156` жёстко ставит `QADAM_APP_MODE: 'DEMO_MODE'`.

**Судьба второго стенда.** После объединения `qadam-production` (Vercel) не
нужен. Проект Supabase `xeawgjbywhubnkuxtgho` **не удаляйте сразу**: на нём
чистая схема без демо-данных, это удобный эталон для сверки и запасной стенд.
На нём же лежит один тестовый арендатор от проверки регистрации, который база
отказалась удалять («нельзя убрать последнего владельца») — это её инвариант
работает правильно, а не дефект.

## 6. Что сделать: список

Порядок осмысленный, но не догма.

1. **Прочитать** PRODUCT_CONSTITUTION, ARCHITECTURE, REAL_VS_MOCK,
   KNOWN_LIMITATIONS и раздел 5 этого документа. Не начинать с кода.
2. **Поднять локально:** `npm ci && npm run dev:all` (нужен запущенный Docker
   Desktop). Убедиться, что `npm run verify` проходит на чистом дереве.
3. **Согласовать с владельцем** изменение правил из DEPLOY_RUNBOOK D/E — это
   решение продукта, а не рефакторинг.
4. **Перевести девять гейтов** на `businesses.mode`; переменную окружения
   свести к потолку стенда. Каждый гейт — отдельная проверка «это решение про
   заведение или про стенд?».
5. **Дать посетителю выбор на входе:** демо-заведение или своя регистрация, на
   одном адресе.
6. **Переписать `mode-separation.mjs`** под доказательство разделения по
   заведениям на одном сервере. Без этого набора объединение недоказуемо.
7. **Обновить документы** в том же коммите, что и код.
8. **Слить базы:** развернуть объединённый стенд на демо-проекте
   `lwqoclhgdvpydaetpypb` (там уже есть данные и метка `demo_environment`).
   Второй проект оставить как эталон.
9. **Прогнать всё против живого стенда:** E2E, `http-suite`, `a11y`. Ожидаемые
   числа — в разделе 4; расхождение объяснить, а не списать на флаки.
10. **Вернуть стенд к исходным данным** после прогонов:
    `remote_demo_reset.sql`, затем `remote_demo_seed.sql`. Судьи должны
    открывать заполненную кофейню, а не следы тестов.

### Чего делать нельзя

- Ослаблять констрейнт `(mode='demo' and is_mock) or (mode='production' and not
  is_mock)` или триггер `mock rows are forbidden in production businesses`.
  После объединения именно они держат всю гарантию честности.
- Удалять строку из `private.demo_environment` на демо-проекте или добавлять её
  на боевой.
- Применять `supabase/seed.sql` где-либо кроме локальной машины.
- Класть `SUPABASE_SECRET_KEY` в переменную с префиксом `NEXT_PUBLIC_`.
  `npm run check:secrets` для этого и существует.
- Коммитить секреты: репозиторий публичный.
