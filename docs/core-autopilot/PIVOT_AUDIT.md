# PIVOT_AUDIT — решение по каждой части существующего продукта

Дата: 14 августа 2026. Опирается на [PROJECT_STATE.md](PROJECT_STATE.md).

Продуктовая формула пивота:

> Другие системы показывают склад. QOR показывает решение.

Единственный герой: **Decision Contract** — сохраняемый объект решения,
превращающий будущий риск дефицита в конкретный план: что произойдёт,
сколько заказать, у кого, почему, чем грозит бездействие и кто подтвердил.

---

## 1. Правила, которым подчинён весь пивот

1. Таблицы и старые миграции не удаляются. Только forward-only.
2. Никакого destructive reset.
3. Дизайн-система, layout shell, motion и палитра сохраняются как есть.
4. В новый основной поток не попадают: кампании, лояльность, QR, награды,
   nearby, клиентская CRM, Telegram Mini App.
5. Старый экран можно скрыть из навигации, наполнить новым смыслом или
   оставить legacy — но не сломать.
6. Технический каркас переиспользуется; старый продуктовый смысл — нет.

### 2.2 Переделать — каркас остаётся, содержимое меняется

| Существующая часть | Решение | Что станет новым |
|---|---|---|
| `/app/today` — экран «Сегодня» с сигналом выручки | заменить payload | Quiet Morning Queue: 3–5 решений на сегодня вместо одного маркетингового сигнала |
| `recommendations` + FSM `pending/accepted/snoozed/rejected` | расширить полями решения | станет хранилищем Decision Contract: риск, количество, поставщик, отклонённая альтернатива, цена бездействия |
| `/app/supply` — цены поставщиков | расширить | к цене добавляются срок поставки, надёжность, минимальная партия; экран становится частью Supplier Compare |
| `supply_items` | расширить, не ломая | добавляются единица, упаковка, минимальная партия, срок годности, точка перезаказа |
| `supply_offers` | расширить | добавляются lead time и связь с поставщиком как сущностью, а не строкой |
| `/app/analytics` | заменить payload | KPI снабжения: позиции на исходе, среднее время доставки, доля срывов, замороженные деньги |
| `/app/inbox` — центр обращений с триажем | переиспользовать каркас разбора | станет Messenger Stock: тот же поток «входящее → разбор → подтверждение», другой предмет разбора |
| `/app/automations` | заменить payload | правила автозаказа: порог, расчёт количества, границы бюджета |
| `automations` + `automation_runs` | переиспользовать | триггер, guardrails и идемпотентные прогоны подходят под автозаказ без изменений схемы |
| `forecast_runs` | переиспользовать | под прогноз спроса вместо прогноза выручки |
| `/admin/categories`, `/admin/templates`, `/admin/tools` | заменить содержимое | категории товаров, шаблоны поставщиков, набор инструментов снабжения |
| `impact_baselines`, `impact_measurements` | переиспользовать | под эффект снабжения; в демо verified остаётся нулём |
| `transactions`, `transaction_items` | переиспользовать как есть | становятся историей продаж — входом прогноза спроса |
| Лендинг: 14 секций | **уже переделан 14.08** | тексты и цифры под снабжение, вёрстка и анимации не тронуты |
| `/features/*`, `/solutions/*` | **уже переделаны 14.08** | 9 модулей снабжения и 4 отраслевых профиля |

### 2.3 Скрыть из основной навигации, оставить legacy

| Существующая часть | Решение | Почему не входит в финальный кейс |
|---|---|---|
| `/app/campaigns` и студия кампаний | убрать из меню | маркетинг, а не снабжение; ровно тот случай «слишком много функций», за который сняли баллы в отборе |
| `/app/customers`, `/customers/*` | убрать из меню | клиентская CRM в кейсе про поставщиков не оценивается |
| `/app/segments` | убрать из меню | сегментация гостей вне темы |
| `/app/loyalty`, `/q/[token]`, `qr_codes` | убрать из меню | лояльность и QR прямо названы вне нового потока |
| `/app/content` | убрать из меню | контент-студия вне темы |
| `/nearby`, `/nearby/[slug]` | убрать из меню и из sitemap | гиперлокальные скидки вне темы |
| Telegram Mini App `/tg/*` (гостевые экраны) | оставить, из меню не вести | код рабочий, `/tg/owner/supply` пригодится под Messenger Stock |
| `/features` старые URL | **уже переименованы** через `git mv` | история файлов сохранена, мёртвых ссылок нет |

Все перечисленные маршруты остаются рабочими по прямому адресу. Их RLS,
тесты и данные не тронуты — это снимает риск каскадных падений.

### 2.4 Удалить

**Ничего не удаляется на этом этапе.**

Единственный кандидат — `src/services/qadamService.ts`: он не импортируется
ни одним файлом, это мёртвый код. Но и он остаётся: удаление не даёт
выигрыша, а любое движение файлов перед дедлайном — лишний риск.

Обоснование общего решения: 12 файлов pgTAP и 5 сценариев Playwright
опираются на маркетинговые таблицы. Удаление таблицы уронит их каскадом,
а времени на переписывание тестов до 15 августа нет.

### 2.5 Создать с нуля

| Что | Почему нельзя переиспользовать |
|---|---|
| События остатка (приёмка, расход, списание, перемещение) с идемпотентностью | `supply_items` хранит текущую цену, а не движение; событийная модель обязательна, чтобы остаток не редактировался напрямую |
| Политика пополнения: точка перезаказа, страховой запас, упаковка, минимальная партия, срок годности | в схеме нет ни одного из этих полей |
| Расчёт часов до нуля и разрыва до поставки | новая формула, аналога в домене нет |
| Прогноз спроса: скользящее среднее 28 дней, коэффициент дня недели, ошибка на бэктесте | `signals.ts` сравнивает окна, но не прогнозирует |
| Календарь локальных событий и коэффициенты с меткой «гипотеза» | новой сущности нет вообще |
| Заказы поставщикам и их позиции | `campaigns` не годятся даже как каркас: другой жизненный цикл |
| Приёмка и расхождения | нет аналога |
| Надёжность поставщика: доля вовремя и полностью, сглаживание малой выборки | нет аналога |
| Обезличенный общий рейтинг поставщиков | нет аналога |
| Решатель разделения заказа между поставщиками | нет аналога |
| Входящие сообщения мессенджера с разбором и подтверждением | `inquiry-triage.ts` разбирает обращения гостей — другой предмет, но каркас потока переиспользуется |

## 3. Что решено не трогать сознательно

**Глобальное переименование кода.** В интерфейсе продукт называется QOR
Autopilot: логотип, тексты, метаданные, манифест. Внутри кода остались
`qadam-growth-os`, `src/server/qadam/`, `QadamSignal`, префиксы в БД.
Переименование затронуло бы 296 файлов, все импорты, генерируемые типы и
61 миграцию ради нуля баллов по критериям кейса.

**Экран `/app/today`.** Он остаётся рабочим и завязанным на кампании —
это единственный экран кабинета, показывающий живые данные из базы.
Очередь решений живёт на новом `/app/decisions`, а `today` переделывается
содержимым на следующем этапе.

## 4. Чистка навигации, выполненная в этом этапе

Правки минимальные и данных не касаются.

| Было | Стало | Причина |
|---|---|---|
| «Остатки из чата» вела на `/app/inbox` (центр обращений гостей) | ведёт на новый `/app/messenger-stock` с описанием будущего экрана | пункт обещал одно, а открывал другое |
| «Правила автозаказа» вели на `/app/automations` (маркетинговые автоматизации) | ведут на новый `/app/reorder-rules` | то же самое |

Оба старых маршрута остались рабочими по прямому адресу и указаны как
запасной переход внутри новых страниц.

Ранее в этот же день из меню уже были выведены кампании, клиенты, сегменты,
контент и лояльность, а поиск в шапке переведён с клиентов на остатки.

## 6. Блокеры для следующего этапа

| Блокер | Влияние | Что нужно |
|---|---|---|
| Docker Desktop не запущен | нельзя применить новые миграции, перегенерировать типы, прогнать pgTAP, E2E, security и a11y | запустить Docker Desktop, дальше `npm run dev:all` поднимет всё сам |

Первый блокер жёсткий: без него этап 1 нельзя завершить, потому что новая
схема данных не применится и типы разойдутся с базой. Написать миграции и
доменную логику можно и без него — проверить нельзя.
